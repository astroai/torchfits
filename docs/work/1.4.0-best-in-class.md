# Plan: 1.4.0 — the FITS release to beat (2026-11-28)

Status: PROPOSED. Owner: maintainer. Scope: everything that ships in **1.4.0**.
Work so far on `main` (the correctness wave, streaming writes, native
`where=`, fpack controls, scale and CFITSIO hardening; see `docs/roadmap.md`)
is the starting point, not a release: nothing is tagged until this plan's
exit gate passes.

**Release policy.** 1.4.0 carries all of this plan. **1.4.1 and later are
patch releases only**: bug fixes and newer vendored CFITSIO (new upstream
releases and security backports). No new features, no new public API, no
behaviour changes beyond the fix itself, no dependency-floor raises unless a
fix or CFITSIO update requires one. New features wait for 1.5.

**Goal.** At 1.4.0, torchfits is the best FITS software on
every axis we can measure — performance, functionality, usability, docs and
reliability — against every earlier torchfits release and every other FITS
implementation, with the evidence published by torchfits-harness.

**Two flagship tracks.** Above everything else, torchfits must be excellent,
robust and fast at (1) **ML pre-processing transforms** (§ML) and (2)
**remote and cached fetching** — S3 and other object stores, VOSpace, HTTP,
and shared filesystems such as `$PROJECT` or CANFAR `/arc` — into a local
NVMe cache (`$SLURM_TMPDIR`, CANFAR `/scratch`, cloud instance disks) laid
out for the shortest path into device memory (§RC). These two tracks come
first in the milestones and get their own exit criteria.

**Boundary.** 1.5 starts direct-to-GPU reads, torchfits' own tile codecs and
the work shared with other astronomy formats (heading to 2.0). Nothing in this
plan may need those, but the §RC cache layout must be the one 1.5's
GPU-direct path reads from, so it is designed for that now. The 1.x read and
write calls stay compatible; every behaviour change ships with a note in
`docs/compatibility.md`.

This file is a temporary plan: it lives in `docs/work/` and is deleted in the
commit that tags 1.4.0.

## 0. Definition of done (the 1.4.0 exit gate)

The 1.4.0 tag ships only when all of these hold, each produced by one
harness command and published in its docs:

1. **Performance scorecard.** For every case in the harness matrix (§H2),
   torchfits is fastest, or within the measured noise floor of the fastest,
   against every comparator in §H1, on Linux x86_64 and macOS arm64, mmap on
   and off. Any case that is not #1 is listed with a measured cause and an
   accepted reason (for example "CFITSIO's serial HCOMPRESS encoder; own codec
   in 2.0").
2. **No regression versus any earlier release** (1.0 … 1.4.n−1) beyond noise,
   in time or peak memory, on any case.
3. **Feature matrix.** Every row of the FITS 4.0 coverage matrix (§F) is
   Supported or explicitly Out of Scope with a reason; no Partial rows.
4. **Correctness.** Bit-exact read parity with CFITSIO direct / fitsio /
   astropy on the full real-archive corpus (§H4); every file torchfits writes
   passes `fitsverify` with zero errors and reads identically in astropy,
   fitsio and CFITSIO.
5. **Usability.** Every task in the cross-library cookbook (§H6) has a
   torchfits recipe with no more lines than the best competitor's, and every
   error a user can trigger names the file, HDU, column or keyword involved.
6. **Docs.** Every public symbol, CLI flag, environment variable and exit code
   is documented once and tested (docs-contract); migration guides exist for
   each comparator; performance guidance is backed by scorecard numbers.
7. **Reliability.** Fuzzing and sanitizer lanes run in CI on every PR; native
   line coverage and public-surface coverage meet their targets (§R).
8. **ML pre-processing (§ML).** On each reference workload (§ML "GPU never
   idle") the training step with the torchfits loader is within 5 % of the
   same step fed from a perfect in-memory loader, and every transform is
   faster than its astropy/photutils/numpy equivalent on the same device,
   with numerically matching results.
9. **Remote and cache (§RC).** From each supported source (S3-compatible,
   VOSpace, HTTP, shared filesystem) the time to first batch and the
   steady-state throughput beat the best alternative workflow (astropy +
   fsspec, `aws s3 cp`/`rclone` staging, `vcp`, plain `cp`/`rsync` to
   `$SLURM_TMPDIR`), with zero corrupt or partial cache entries under
   fault injection, and a warm-cache epoch reading NVMe → pinned host → device
   with no decode or byte-swap on the hot path.

## ML. ML pre-processing transforms (flagship)

**Today.** `torchfits.transforms` has about 40 transforms (stretches,
robust/zscale/percentile/sigma normalizers, background and mesh background,
sigma clipping, DQ/ivar/NaN masks, Lupton RGB), `Compose`/`as_module`, the
`Payload` with inverse variance and masks, calibration `DataState` checks and
per-payload inverse statistics. Most run on GPU; some (zscale, percentile,
mesh background) are slow there. Datasets cover images, cubes, spectra,
tables, cutouts and staged cutouts, with lazy table access.

| ID | Item | Prio |
|---|---|---|
| ML-1 | **Batched device-resident transforms**: every transform accepts `(B, C, ...)` batches on CUDA/MPS/CPU with no per-sample Python loop and no host synchronisation (`.item()`, `.cpu()`, data-dependent shapes) on the hot path | P1 |
| ML-2 | **Fast robust statistics on device**: percentiles, medians, MAD, zscale, sigma clipping and mesh background via batched selection (`kthvalue`/sort on bounded samples, histogram-based quantiles) instead of full `torch.quantile` copies; documented accuracy versus astropy | P1 |
| ML-3 | **`torch.compile` and CUDA graphs**: the standard pipelines compile without graph breaks; fused stretch+normalize+clip kernels where compile does not fuse; eager vs compiled published | P1 |
| ML-4 | **Robustness**: uniform NaN/Inf/masked/ivar semantics across all transforms; all-masked, empty, constant and saturated inputs; dtype preservation (fp16/bf16 safe numerics); exact inverses where defined; property-based fuzz tests of every transform; deterministic seeding for stochastic ones | P1 |
| ML-5 | **Loader to device**: pinned-memory batches, `non_blocking` copies and a device prefetcher (CUDA stream) in `make_loader`; transforms applied on device after the copy; variable-shape collation (padding, bucketing) for spectra and cutouts | P1 |

**"GPU never idle" — recommended definition (confirm).** Hardware-independent:
for each reference workload, measure the training step time fed by a perfect
loader (the same batches preloaded in device memory) and by the torchfits
loader from a warm local cache; the ratio must be ≤ 1.05 using no more
DataLoader workers than CPU cores. Run it on the fastest GPU available in a
CANFAR session (the hardest case, since faster GPUs starve first), on one
mid-range NVIDIA GPU, and on Apple MPS. Reference workloads, each built from
existing examples:

| Workload | Data | Model |
|---|---|---|
| Cutout classification | 64–128 px multi-band cutouts (Galaxy Zoo / Legacy Survey) | ResNet-18 |
| Image-to-image | 512² tiles from MEF CCD frames (MegaCam denoising) | U-Net |
| Spectra | 1-D spectra with ivar and mask (SDSS/DESI) | 1-D CNN |
| Catalog rows | table rows with `where=` selection (Gaia-like) | MLP |
| ML-6 | **Astronomy-aware augmentation**: flips/rot90/crops/random cutouts, flux-preserving rebinning, noise injection from inverse variance, mask-aware ops; all batched and seedable | P2 |
| ML-7 | **Multi-band and multi-HDU samples**: SCI/IVAR/MASK/DQ assembled per sample from one or many files with shape validation (staged cutouts already check), band registration by HDU name | P2 |
| ML-8 | **Recipes per survey**: HST, JWST, Euclid, Rubin, Legacy Survey, SDSS/DESI spectra — tested pipelines in the docs and examples, with the measured loader throughput | P2 |

Comparators (harness): astropy.visualization (`ZScaleInterval`,
`AsinhStretch`, ...), `astropy.stats.sigma_clip`, photutils `Background2D`,
numpy/scipy baselines, kornia/torchvision for generic ops, and a plain
fitsio/astropy + DataLoader pipeline end to end.

## RC. Remote and cached fetching (flagship)

**Today.** HTTP(S) and VOSpace (`vos:`/`vault:`) sources download into a
disk cache (`TORCHFITS_CACHE_DIR`, `TORCHFITS_REMOTE_CACHE`); downloads resume
with `If-Range`, are validated as complete FITS before promotion, are atomic
and use a cross-process lock; staged cutout datasets stage into
`SLURM_TMPDIR`/`TMPDIR` and clean up; prefetch is scoped per iterator; HTTP
Range reads exist for uncompressed 2-D cutouts only. There is no S3/GCS/Azure
support, no cache size management, and the cache stores raw FITS bytes.

| ID | Item | Prio |
|---|---|---|
| RC-1 | **Object stores**: S3 and S3-compatible endpoints (MinIO, Ceph, CANFAR/Arbutus object storage), GCS and Azure; Range GETs and parallel multipart fetch; credentials from the standard environment/profile chain, never logged. Backend: see the recommendation below | P1 |
| RC-2 | **Filesystem sources as first-class**: `$PROJECT`/Lustre/GPFS/CephFS/`/arc` paths staged to node-local NVMe (`$SLURM_TMPDIR`, CANFAR `/scratch`) with large aligned copies, parallel streams and `copy_file_range`/`sendfile` where available; cache validity from (size, mtime, inode) instead of HTTP validators | P1 |
| RC-3 | **Tiered cache with a budget**: source → node-local cache → per-job scratch; size budget with LRU eviction, pinning of a dataset's working set, cross-process and multi-rank safety (one fetch per node, others wait), resume, retries with backoff, offline mode, `torchfits cache` CLI (`ls`, `du`, `stage`, `verify`, `prune`) | P1 |
| RC-4 | **Decoded cache layouts (both)**: `layout="fits"` stores an uncompressed FITS copy (portable: every FITS tool reads it; mmap-able); `layout="blocks"` stores native-endian, page-aligned blocks (tile- or row-band-sized, in the dtype the consumer asked for) plus a small index — a warm read is NVMe → pinned host → device with no decompression or byte-swap, and it is the layout 1.5's GPU-direct (GDS/`cuFile`) path will read. Both are derived entries keyed by the source version, invalidated with it, and counted in the cache budget; keeping the original download alongside is optional | P1 |
| RC-5 | **Partial remote reads** (with PF-3): byte-range cache of headers, tiles and row windows instead of whole files; concurrent Range requests; compressed images fetch only the tiles a cutout needs; tables fetch only requested columns' row windows | P1 |
| RC-6 | **Staging API**: `torchfits.stage(sources, to=..., decode=..., workers=...)` and a dataset option to stage the whole working set before the first epoch, with progress, manifest, integrity (`DATASUM` when present) and cleanup at job end; profiles auto-detected from `SLURM_TMPDIR`, CANFAR and cloud instance storage | P1 |
| RC-7 | **Fault injection and integrity**: truncated bodies, dropped connections, throttling, 5xx/429, expired credentials, disk full on the cache, concurrent writers, kill -9 mid-promotion — never a corrupt or partial cache entry, always a typed error or a successful retry | P1 |
| RC-8 | **Observability**: cache hit/miss, bytes fetched, time to first byte and per-source throughput available through `get_cache_stats()` and a debug log, so users can see why an epoch is slow | P2 |
| RC-9 | **Security**: keep the SSRF guard for HTTP; signed URLs and credential scopes for object stores; no secrets in URLs, logs or cache paths | P1 |

**S3 backend — recommendation (confirm).** Use `obstore` (Python bindings to
the Rust `object_store` crate that Polars and DataFusion use) as an optional
extra, `torchfits[cloud]`, for authenticated S3, GCS and Azure: it already
handles the credential chains (environment, profiles, instance roles, SSO),
retries and concurrent Range requests, ships wheels for every platform we
build, and adds no Python dependency tree. Public and presigned object URLs
keep going through torchfits' own HTTP stack with no extra dependency. Do not
write a native SigV4 client: the credential-chain and signing surface is large
and security-sensitive for little speed gain. Do not depend on `fsspec`/`s3fs`
(pure Python, slower, heavy dependency chain); optionally accept an `fsspec`
filesystem object a user passes in, as an escape hatch. Harness H10 benchmarks
the chosen backend against `s5cmd`, `aws s3 cp`, `rclone` and astropy +
`fsspec` before this is locked in.

Comparators (harness): astropy `fits.open(..., use_fsspec=True)` with
`section` reads, s3fs/fsspec raw reads, `aws s3 cp`/`s5cmd`/`rclone` staging,
VOSpace `vcp`, `cp`/`rsync` from a shared filesystem, and fitsio on a locally
staged copy. Metrics: time to first batch, steady-state samples/s, bytes over
the network, cache hit rate, GPU idle fraction.

## 1. Performance workstream

Targets are relative to the best comparator per case. Every item lands with a
harness case (new if missing) and before/after numbers from the same host.

### P1 — must land in 1.4.0

| ID | Item | Today | Target |
|---|---|---|---|
| PF-1 | **Parallel tile decompression** for RICE/GZIP/HCOMPRESS/PLIO images (row bands of tiles on separate read-only handles, or a tile-range API over CFITSIO's decoders) | Serial per HDU | Near-linear to 4 threads on full reads and large cutouts; no loss on single-tile reads |
| PF-2 | **Parallel tile compression** on write (`write(compress=…)`, `compress` CLI, streaming image writer) | Serial per HDU; `-J` only across files | Near-linear to 4 threads; byte-identical output to the serial path for a fixed dither seed |
| PF-3 | **Remote partial reads beyond uncompressed 2-D**: compressed images fetch only the tiles a cutout needs; scaled images; cubes; tables with row windows, column projection and `where=` | Full download | Bytes fetched ≈ bytes needed + headers; concurrent Range requests; byte-range cache |
| PF-4 | **Small-call overhead**: tiny image read, header/key reads, `read_batch`, dataset `__getitem__` | Tiny read ≈ 30 µs; small float32 +7 % vs 1.3.3 | Tiny read ≤ fitsio; fast path for repeated small reads in ML loops |
| PF-5 | **VLA throughput**: bulk heap decode (no per-row Python objects), device gather | `varlen_*` slowest table family | ≥ fitsio and astropy on every `varlen_*` case |
| PF-6 | **Native `read_torch(where=)`**: align the torch and Arrow predicate dialects (literal coercion, unsigned, scaled) so it uses the native windowed scan | Windowed torch evaluation | Same results; native speed; memory = result + one window |

### P2 — should land

| ID | Item |
|---|---|
| PF-7 | `read_batch` / dataset prefetch: overlap opens and reads across files with a bounded in-flight window; parallel open path |
| PF-8 | `.fits.gz` random access: benchmark the gz index against fitsio/astropy, tune index spacing, cache across handles |

## 2. Functionality workstream (FITS 4.0 coverage)

### F — coverage matrix to close

| ID | FITS feature | Today | 1.4.0 target | Prio |
|---|---|---|---|---|
| FN-1 | **Tiled table compression** (`ZTABLE`, FITS 4.0 §10.3; `fpack -table`) | Not read or written | Read (all column codecs) and write; streaming writer support; `compress`/`decompress` CLI | P1 |
| FN-2 | **64-bit `Q` heap descriptors on write** | Readers accept `Q`; writers emit `P` | Automatic `Q` when the heap exceeds 2 GiB; test past 2 GiB | P1 |
| FN-3 | **Streaming image writer** (`torchfits.image.writer()` or section writer), incl. tile-compressed and checksum | Images must fit in memory | Out-of-core mosaics/cubes; atomic publish; bounded memory | P1 |
| FN-4 | **In-place image section updates** (`write_subset` for uncompressed images) | Whole-file rewrite only | `pwrite`/mmap update of a region; checksum refresh; atomic semantics documented | P1 |
| FN-5 | **Random groups** (`GROUPS=T`, UVFITS) | Refused | Read: group parameters as a table + data as a tensor; write optional | P2 |
| FN-6 | **`A3DTABLE`** (legacy binary-table name) | Unsupported | Read as `BINTABLE` | P2 |
| FN-7 | **`INHERIT` convention** | Ignored | `read_header(..., inherit=True)` and HDU objects honour it | P2 |
| FN-8 | **String arrays with `TDIM`** | One string per row; TDIM lost through Arrow | Shaped read with `shape_cells=True`; TDIM kept on write | P2 |
| FN-9 | **Nested columns with nulls** | Written as VLA (lossy layout) | Fixed vector + `TNULL`/NaN; round-trip keeps TFORM | P2 |
| FN-10 | **Streaming table writer gaps** | No append-as-HDU, no `quantize=`, integer nulls need explicit `tnull` | All three supported | P2 |
| FN-11 | **Header conventions**: HIERARCH and CONTINUE round trip on write, long-string keywords, in-place header edits that reuse header padding | Partly covered | Full round trip, no file rewrite when space allows | P2 |
| FN-12 | **`verify`**: structural checks for `.gz`/`.bz2` and remote files; optional fitsverify-equivalent checks (keyword order, mandatory keywords, padding) | Local uncompressed only | Parity with fitsverify verdicts on the corpus | P2 |
| FN-13 | **FITS time standard columns** (`TIMESYS`, `MJDREF`, `TIMEUNIT`) → Arrow timestamps in interop (metadata only, no WCS) | Not interpreted | Opt-in conversion in `to_arrow`/`to_pandas`/`to_polars` | P3 |
| FN-14 | **Grouping convention** (`GROUPING` tables) | Not supported | Read helper listing members | P3 |

Out of scope (unchanged): WCS evaluation, units, catalog cross-match, source
finding, spectroscopy transforms.

### CLI parity

Every common task done today with fpack/funpack, imcopy, fitscopy,
fitsverify, the ftools `ftlist`/`ftcopy`/`fstruct`/`fthedit`, and STILTS
`tcopy`/`tpipe` (selection, projection, format conversion) has a torchfits CLI
equivalent that is at least as fast and documented in `docs/cli-recipes.md`
with the side-by-side command. Decide `imexpr` (expression CLI) here: either
spec it as part of this parity work or drop it from the backlog.

## Milestones (all before the 1.4.0 tag)

These are internal checkpoints on `main`, not releases. Each one lands with
every current gate green and the harness scorecard showing no regression; a
release candidate (`1.4.0rcN`) may be cut at any checkpoint for testing, but
nothing is tagged final until M7 passes.

1. **M1 — measurement first**: prove CI on GitHub Actions (RE-6); land the
   harness H3 methodology and H8 PR gate so every later milestone is measured.
2. **M2 — ML pre-processing**: ML-1…ML-5 with the H9 lane; PF-4 (small-call
   overhead) because ML loops are dominated by it.
3. **M3 — remote and cache**: RC-1…RC-7 and RC-9 with the H10 lane, together
   with PF-3 (partial remote reads, = RC-5).
4. **M4 — native throughput**: PF-1, PF-2, FN-2, PF-5, PF-6 (parallel tile
   decode also feeds RC-4's decoded cache).
5. **M5 — out of core and format completeness**: FN-3, FN-4, FN-10, FN-1,
   FN-5…FN-9, FN-11.
6. **M6 — usability and CLI parity**: US-1…US-6, CLI parity, FN-12, `imexpr`
   decision, H6 cookbook, ML-6…ML-8, RC-8.
7. **M7 — docs and reliability**: DO-1…DO-7, RE-1…RE-5, remaining P2/P3,
   H1/H4/H5 complete, then the §0 exit gate and the **1.4.0 tag**.

After 1.4.0: **1.4.x patch releases** take only bug fixes (each with a
regression test) and CFITSIO updates (new upstream releases re-vendored with
the patch set re-checked; local patches dropped once upstream carries them),
under the policy at the top of this plan.

Decisions needed from the maintainer before M2: US-7 (`shape_cells`
default, `NOT` null semantics), US-8 (Windows), `imexpr` keep/drop, the H1
comparator list (which Java/Rust/Julia lanes are worth maintaining). For the
flagship tracks, recommendations are recorded above and need confirmation:
RC-1 backend (`obstore` as an optional extra), RC-4 (both cache layouts), and
the "GPU never idle" definition (loader overhead ≤ 5 % against a perfect
in-memory loader on four reference workloads).
